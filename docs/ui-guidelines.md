# Make one web UI feel native on five platforms

Most of what users call "basic" or "careless" UI is the same on every platform. The shared floor is **WCAG 2.2 AA**: targets of at least 24×24 CSS px, 4.5:1 contrast for text and 3:1 for controls, focus that is visible and never hidden, sign-in where paste and password managers work, errors described in text with a fix, status messages announced, and layouts that survive 320 px width and 200% text ([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)). On top of that sit a few well-sourced web habits: correct `autocomplete`, buttons named with verbs, exactly one highlighted navigation item, Back that goes up one step, loading indicators chosen by wait time, media that pauses when the page is hidden, and permissions asked only when the user starts the feature that needs them. The platform layer differs on a small, predictable set of points: dialog button order, where Settings lives, whether an in-app theme picker is allowed, keyboard shortcuts, capitalisation, how Back is triggered, and what an app may do after its window closes. For Kagaz the biggest risk is not the shared rules. It is the behaviour a Tauri web view does not provide for free: the iOS edge-swipe back, the Android predictive-back callback, the macOS Edit menu that makes Cmd+C and Cmd+V work, Alt+Left and the mouse Back button on Windows, the system dark mode inside WebKitGTK, safe-area insets, and the arrow (not hand) cursor on desktop buttons. Where sources are weak the report says so: Material 3 pages could not be read, so Material-specific rules are second-hand; Windows tray and window rules exist only in Microsoft's Windows 7 guide; and several web-view behaviours still need testing on real devices.

## How to read the rule tables

Every rule is one sentence you can check by looking at a screen or pressing a key. Each rule has an ID (S = shared, A = Android, I = iPhone, W = Windows, M = macOS, L = Linux) so it can be cited in reviews and commits. A rule with no tag comes from an official primary source that the researchers read directly: W3C, MDN, web.dev, Android Developers, Apple's HIG and developer documentation, Microsoft Learn, the GNOME and KDE HIGs, libadwaita, freedesktop.org, and the Tauri docs. Non-official sources (NN/g and GOV.UK) are tagged in the source column. The tags mean:

| Tag | Meaning |
|---|---|
| **[Secondary]** | The official page could not be read; the rule rests on a search summary or a secondary write-up |
| **[Win7 guide]** | Official Microsoft text, but from the Windows 7 UX guide, which says it "has not been updated for newer versions of Windows" |
| **[Unofficial]** | From developer blogs, community posts or bug trackers, not a platform owner |
| **[Inference]** | No source says it in these words; it follows from the cited rule(s) and needs confirming |
| **[Unverified]** | The rule is sound, but how a Tauri web view behaves here has not been tested on a device |

NN/g and GOV.UK are respected but not platform owners. Their rules are kept untagged because they are published design guidance rather than opinion, but the source column always names them.

## WCAG 2.2 and web basics set one shared floor

WCAG 2.2 became a W3C Recommendation on **12 December 2024** ([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)), and every platform guide points at the same thresholds. Android's **4.5:1 for text under 18 sp** and Apple's **4.5:1 up to 17 pt** are both the WCAG AA figure under another name ([Android a11y](https://developer.android.com/guide/topics/ui/accessibility/apps); [Apple Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). The only real disagreement is target size: **24 CSS px** (WCAG AA), **28 pt** (macOS default controls), **40 epx** (Windows touch), **44 pt** (Apple) and **48 dp** (Android). One CSS px in a system web view is roughly one dp or pt, so 48 CSS px on touch layouts satisfies all of them. That conversion is an inference the researchers did not measure.

### Layout, text size, safe areas and dark mode

The CSS for safe areas works on every platform: **`env(safe-area-inset-*)` returns 0 on rectangular screens**, so the same rule is harmless on desktop ([MDN env()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env)). On iOS the insets are non-zero only when the viewport meta tag includes `viewport-fit=cover` ([WebKit blog](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)). Text scaling is the gap the notes left open. Android scales fonts to **200%** ([Android 14](https://developer.android.com/about/versions/14/features)), iOS Dynamic Type to at least **200%** ([Apple Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)), and Windows text size to **225%** ([Text scaling](https://learn.microsoft.com/en-us/windows/apps/design/input/text-scaling)). How each Tauri web view passes those settings into CSS was not researched, so the test is to turn the system setting to its maximum and look.

### Forms and sign-in keep the password manager working

Kagaz's cloud sign-ins (such as the Tapo email, then password, then MFA code flow) are where WCAG 2.2's newest criterion matters. **3.3.8 Accessible Authentication** treats password managers and paste as the required "mechanism". Blocking paste is a named failure (F109), and "a service that requires manual transcription of a verification code is not compliant" ([W3C Understanding 3.3.8](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html)). Apple adds a practical reason for using one real input: a custom code view built from separate boxes "cannot show the AutoFill UI" ([Apple Password AutoFill](https://developer.apple.com/documentation/security/enabling-password-autofill-on-a-text-input-view)).

### Errors and states explain themselves in plain words

NN/g's timings give the loading rules. Show **nothing under about 1 s**, a **spinner for one module loading in 2–10 s**, a **skeleton for a whole screen under 10 s**, and above 10 s "an explicit estimation of duration" ([NN/g Skeleton screens](https://www.nngroup.com/articles/skeleton-screens/), non-official). Apple adds that a spinner and a progress bar should never swap with each other, and that vague captions like "Loading" should be avoided ([Apple Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators)). KDE adds a rule that fits a device app well: when a printer or camera fails, say so, and "never let the user blame your app" for a third-party fault ([KDE Status changes](https://develop.kde.org/hig/status_changes/)).

### Buttons and confirmations name the outcome

Every platform agrees on how buttons are labelled and when to confirm. Apple says never Yes or No and always "Cancel" ([Apple Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)). Microsoft wants "specific responses" such as Delete or Cancel ([Windows Dialogs](https://learn.microsoft.com/en-us/windows/apps/design/controls/dialogs-and-flyouts/dialogs)). GNOME says "Save" or "Print", not OK ([GNOME Dialogs](https://developer.gnome.org/hig/patterns/feedback/dialogs.html)). All of them prefer undo to a confirmation. ### Live media pauses when nobody is watching

MDN gives two facts that matter for a camera app. Hidden pages get throttled timers, but **pages playing audio or using WebSockets or WebRTC are exempt**. Tauri web views can configure autoplay differently from browsers. That was not researched, so the fallback in S77 is required, not optional.

## Android expects predictive back, edge-to-edge and typed background work

Android 16 changes two things a web-view app must handle in native code. For apps targeting **API 36**, "`onBackPressed` is not called and `KeyEvent.KEYCODE_BACK` is not dispatched anymore", and the opt-out from edge-to-edge "is deprecated and disabled" ([Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)). Predictive back therefore has to know before the gesture starts whether the page has something to close. Kagaz needs one `OnBackPressedCallback` that stays enabled only while the page reports an open overlay or a non-Home screen, and is **disabled at Home so the system back-to-home animation plays** ([Predictive back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)). Whether Tauri already wires this up was not checked. The other big item is the listener that keeps running after close: Core app quality lists "maintaining a network connection for notifications" as a poor use of background services ([Core app quality](https://developer.android.com/docs/quality-guidelines/core-app-quality)), so it needs a typed foreground service, a visible notification and a written justification. ## iPhone expects an edge swipe, safe areas and Dynamic Type

The HIG was read in full through Apple's JSON feed, so the iOS rules are among the best-sourced in this report. The most important gap is one Kagaz has to build itself: **`WKWebView.allowsBackForwardNavigationGestures` defaults to false** ([WKWebView docs](https://developer.apple.com/documentation/webkit/wkwebview/allowsbackforwardnavigationgestures)), and even when turned on it moves through page history, not an in-page screen stack. Meanwhile native apps pop on a left-edge swipe ([interactivePopGestureRecognizer](https://developer.apple.com/documentation/uikit/uinavigationcontroller/interactivepopgesturerecognizer)), and since iOS 26 on a horizontal pan anywhere in the content ([interactiveContentPopGestureRecognizer](https://developer.apple.com/documentation/uikit/uinavigationcontroller/interactivecontentpopgesturerecognizer)). App Review adds the stakes for a web shell: the app must have UI that elevates it "beyond a repackaged website" ([App Review 4.2](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)). Apple also takes the firmest position of any platform on theme: "Avoid offering an app-specific appearance setting" ([Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)).

A WebView2 single-page app gets neither Alt+Left nor the mouse Back button for free. DOM mouse buttons 3 and 4 map to XButton1 and XButton2, and the app must route them to its own Back.

That is the one desktop where Kagaz's "keep listening after close" is the normal pattern.

## GNOME and KDE disagree with each other more than with anyone else

Linux is two platforms. GNOME wants a client-side **header bar** with Back on the left, the title or view switcher in the centre and a "Main Menu" at the right ([Header bars](https://developer.gnome.org/hig/patterns/containers/header-bars.html)). KDE wants a toolbar under a system-drawn title bar ([KDE Layout](https://develop.kde.org/hig/layout_and_nav/)). They also disagree on capitalisation, the Preferences shortcut (Ctrl+, against Ctrl+Shift+,), reload (Ctrl+R against F5) and the tray. Stock GNOME has none: the GNOME design wiki calls it deprecated ([GNOME wiki](https://wiki.gnome.org/Design/OS/MessageTray/Compatibility)), and its removal in 3.26 is reported only by secondary sources. KDE tolerates a tray only as an opt-in last resort ([KDE Status changes](https://develop.kde.org/hig/status_changes/)) and says plainly "Don't keep running in the background as a System Tray icon when closed" ([KDE Simple by default](https://develop.kde.org/hig/simple_by_default/)). On GNOME the correct route for Kagaz's always-on listener is the **Background portal**, which takes a user-visible reason and an optional autostart flag, plus a status line of at most 96 characters ([Background portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Background.html)). One web-view-specific risk stands out: WebKitGTK's `prefers-color-scheme` was unreliable according to 2019 WebKit bugs ([Bug 196685](https://bugs.webkit.org/show_bug.cgi?id=196685)). Reading the Settings portal's `color-scheme`, `accent-color`, `contrast` and `reduced-motion` keys from Rust is the safer route ([Settings portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html)), but its 2026 state is unverified.

## Five platforms split on button order, settings, theme, shortcuts and case

Disagreements are rare but visible, and users notice them immediately because each one is a muscle-memory habit. The right response for a single web UI is to **detect the OS once (Tauri's `os` plugin), set a `data-os` attribute on the root element, and let one component branch per OS**, rather than picking one platform's habit and imposing it everywhere. That approach is the researchers' recommendation, not a platform rule. The table states the conflict, the sources, and the handling this report recommends.

## Conclusion

The clearest finding is how little of "good etiquette" is platform-specific once the WCAG floor is met. Five design systems written by competing companies agree on verb buttons, undo over confirmation, one highlighted location, explaining empty screens, asking for permissions in context, and staying quiet with notifications while the app is in front. That means about two-thirds of this report can become an automated or per-screen checklist that is identical on every build, and only the platform tables need device testing. The real engineering cost sits in a short list of native glue that Tauri does not supply and that the notes could not confirm it supplies: an Android predictive-back callback driven by page state, an iOS edge-swipe back gesture, a full macOS menu bar, Alt+Left and mouse-Back routing on Windows, OS appearance settings passed into WebKitGTK, and safe-area insets on old Android WebViews. Each of these deserves one targeted test before more UI work.

The second finding is that Kagaz's most distinctive behaviour, listening for doorbells after the window closes, is the one most directly at odds with the guides. KDE forbids it as a tray default, Windows' only guidance says opt-in and via Minimise, Android's quality guide calls notification-only background connections a poor use, and iOS will not allow it at all without push. Only macOS treats it as normal. So it should be a visible, user-chosen setting with an OS-specific mechanism, not a silent default. The open questions to settle on real devices are how each web view maps system text size, whether WebKitGTK now follows the system dark setting, how Tauri's Android shell handles Back and insets, and what button order Material 3 dialogs use.
